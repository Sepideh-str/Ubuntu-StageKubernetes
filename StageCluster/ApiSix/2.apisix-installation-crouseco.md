# Apache APISIX Installation on the Crouseco Kubernetes Cluster

**Document date:** 12 October 2026\
**Status:** APISIX and etcd are installed and healthy; gateway
connectivity has been verified. Application routing is not configured
yet.

## 1. Purpose and scope

This document records the APISIX installation in the offline/internal
Kubernetes environment: versions, internal image locations, Helm values,
local etcd storage, installation commands, validation results,
troubleshooting, and official references.

The installation uses the locally available Helm chart at `/root/apisix`
and pulls container images through the internal registry
`repository.crouseco.com`. It does not install APISIX Ingress Controller
or the APISIX Dashboard.

## 5. Helm values and configuration

Custom values file:

``` text
/root/apisix-values.yaml
```

The file contains the key settings below. This is a reference summary,
not a replacement for the complete file in the cluster; retain the
existing admin settings and other chart defaults.

``` yaml
image:
  repository: repository.crouseco.com/docker-proxy/apache/apisix
  tag: "3.19.0-ubuntu"
  pullPolicy: IfNotPresent

replicaCount: 2

nodeSelector:
  zone: frontend

initContainer:
  image: repository.crouseco.com/docker-proxy/library/busybox
  tag: "1.36"

apisix:
  enableIPv6: false
  admin:
    enabled: true
    enable_admin_ui: false
    type: ClusterIP
    credentials:
      secretName: apisix-admin-credentials

etcd:
  enabled: true
  image:
    registry: repository.crouseco.com
    repository: docker-proxy/bitnamilegacy/etcd
    tag: latest
  replicaCount: 3
  nodeSelector:
    zone: frontend
  podAntiAffinityPreset: soft

ingress-controller:
  enabled: false


global:
  security:
    allowInsecureImages: true
```

The Kubernetes Secret `apisix-admin-credentials` exists in namespace
`apisix`. Its secret values must not be copied into documentation or
source control.

`global.security.allowInsecureImages: true` is set because a
custom/legacy image is used for etcd. Keep this only if required by the
chart's image validation behavior and review it when changing chart
versions.

### Why IPv6 was disabled

APISIX initially crashed during NGINX startup with:

``` text
socket() [::]:9080 failed (97: Address family not supported by protocol)
```

The APISIX configuration had IPv6 enabled, while the worker environment
did not support that IPv6 socket. Setting `apisix.enableIPv6: false`
fixed the startup issue. If IPv6 is enabled on the nodes in the future,
reassess this setting before changing it.

## 6. Persistent storage for etcd

The cluster did not have a StorageClass or dynamic local-volume
provisioner available for these claims. Local PersistentVolumes were
created manually and bound to the etcd PVCs.

Manifest:

``` text
/root/apisix-local-pv.yaml
```

Local directories used:

``` text
/var/lib/k8s-local-storage/apisix-etcd-0
/var/lib/k8s-local-storage/apisix-etcd-1
/var/lib/k8s-local-storage/apisix-etcd-2
```

The directories were placed on the frontend worker nodes according to
the PV node affinity. The three PVs were 8 GiB each, `ReadWriteOnce`,
`Retain`, and used `storageClassName: ""`.

Check the actual mapping and binding:

``` bash
kubectl get pv
kubectl get pvc -n apisix
kubectl describe pv apisix-etcd-pv-0
kubectl describe pv apisix-etcd-pv-1
kubectl describe pv apisix-etcd-pv-2
```

The observed PVCs `data-apisix-etcd-0`, `data-apisix-etcd-1`, and
`data-apisix-etcd-2` were all `Bound`.

**Important storage considerations** - These are node-local disks, not
shared storage. A volume is tied to its worker node; loss of that node
or its disk can make that member's data unavailable. - etcd replicates
its data across members, but replication is not a substitute for backups
and restore testing. - Do not delete the PVs/PVCs as part of routine
APISIX troubleshooting. The PV reclaim policy is `Retain`. - Plan and
test etcd snapshots, recovery, disk monitoring, and a supported upgrade
process before production use.

## 8. Installation procedure

### 8.1 Confirm chart and values

``` bash
grep -n 'version:\|appVersion:' /root/apisix/Chart.yaml
grep -n -A5 -B2 'initContainer:' /root/apisix-values.yaml
grep -n -A5 -B2 'enableIPv6' /root/apisix-values.yaml
```

Render the chart before applying it:

``` bash
helm template apisix /root/apisix \
  --namespace apisix \
  --values /root/apisix-values.yaml \
  > /root/apisix-rendered-final.yaml
```

Review the rendered init container, image references, node selectors,
Service ports, and IPv6 setting:

``` bash
grep -n -A8 -B3 'name: wait-etcd' /root/apisix-rendered-final.yaml
grep -n -A3 -B2 'enable_ipv6' /root/apisix-rendered-final.yaml
```

### 8.2 Create local PVs and verify claims

The local PV manifest was applied after creating the local directories
on the appropriate worker nodes:

``` bash
kubectl apply -f /root/apisix-local-pv.yaml
kubectl get pv
kubectl get pvc -n apisix
```

Do not recreate or delete the existing PVs/PVCs unless performing a
deliberate storage migration.

### 8.3 Install or upgrade APISIX

The command used for the successful deployment was:

``` bash
helm upgrade --install apisix /root/apisix \
  --namespace apisix \
  --values /root/apisix-values.yaml \
  --wait \
  --timeout 10m
```

Successful result recorded:

``` text
Release "apisix" has been upgraded. Happy Helming!
STATUS: deployed
REVISION: 5
```

### 8.4 Verify rollout

``` bash
helm status apisix -n apisix
helm get values apisix -n apisix
kubectl get deployment apisix -n apisix
kubectl get statefulset -n apisix
kubectl get pods -n apisix -o wide
kubectl get svc -n apisix
kubectl get endpoints apisix-gateway -n apisix
```

The observed healthy state was: - Two APISIX pods, both `1/1 Running`,
placed on `stage-workerf1` and `stage-workerf2`. - Three etcd pods, all
`1/1 Running`. - Gateway endpoints `10.0.3.1:9080` and
`10.0.4.173:9080`.

Endpoint IPs are runtime values and may change after a rollout.

kubectl exec -n net-test net-test-f2 -- \
  wget -S -O - http://10.97.220.182/

Observed response:

Connecting to 10.97.220.182 (10.97.220.182:80)

## 10. Issues encountered and resolutions

### Issue A --- etcd PVCs were Pending

**Cause:** No suitable dynamic storage provisioner/StorageClass was
available.

**Resolution:** Created three local PVs, each 8 GiB, with node affinity
and `Retain` policy. The etcd PVCs then bound successfully.

### Issue B --- init container looped with `nc: invalid option -- z`

**Cause:** The original BusyBox image
`repository.crouseco.com/k8s-proxy/busybox:1.27` used BusyBox 1.27.2,
whose `nc` applet did not support `-z`. The chart's init container
command was:

``` sh
until nc -z apisix-etcd.apisix.svc.cluster.local 2379; do
  echo waiting for etcd `date`
  sleep 2
done
```

The etcd Service and endpoints were present; the problem was the init
image's `nc` options.

**Resolution:** Changed the init image to:

``` text
repository.crouseco.com/docker-proxy/library/busybox:1.36
```

The init container then completed successfully.

### Issue C --- APISIX crashed because IPv6 sockets were unavailable

**Cause:** NGINX attempted to bind `[::]:9080`, producing:

``` text
socket() [::]:9080 failed (97: Address family not supported by protocol)
```

**Resolution:** Set `apisix.enableIPv6: false` in
`/root/apisix-values.yaml` and upgraded the release. The APISIX pods
then reached `1/1 Running`.
