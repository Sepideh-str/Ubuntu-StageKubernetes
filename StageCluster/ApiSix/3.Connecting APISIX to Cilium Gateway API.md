# Connecting APISIX to Cilium Gateway API

## 1. Overview

This document describes how APISIX was connected to the existing Cilium Gateway API in the Kubernetes cluster.

The goal is to use Cilium Gateway API as the HTTPS entry point and APISIX as the internal API gateway.

### Traffic flow

```text
External Client
      |
      | HTTPS
      v
Cilium Gateway API
Gateway: shared-gateway
Namespace: gateway-system
      |
      | HTTPRoute
      v
APISIX Gateway Service
Namespace: apisix
Service: apisix-gateway
Type: ClusterIP
Port: 80
      |
      | APISIX API Route (to be configured)
      v
Backend Kubernetes Service
Example: crouseserviceloan.stage.svc.cluster.local:8080
```

**Important:** The connection from Cilium Gateway API to APISIX has been configured. The APISIX routes that forward requests to backend services have not yet been configured as part of this work.

## 3. APISIX Gateway Service

APISIX is exposed internally through a Kubernetes `ClusterIP` Service. It is not directly exposed through a NodePort.

The Service was verified using:

```bash
kubectl get svc apisix-gateway -n apisix
```

Observed output:

```text
NAME             TYPE        CLUSTER-IP      EXTERNAL-IP   PORT(S)   AGE
apisix-gateway   ClusterIP   10.97.220.182   <none>        80/TCP    18h
```

The Service forwards traffic from port `80` to the APISIX proxy listener on port `9080`.

The Service endpoints were verified using:

```bash
kubectl get endpoints apisix-gateway -n apisix
```

Observed endpoints:


The existing Gateway is named `shared-gateway` in namespace `gateway-system`.

It was verified using:


Relevant configuration:

```yaml
  gatewayClassName: cilium-nodeport
```

## 5. HTTPRoute Connecting Cilium to APISIX

An HTTPRoute was created in the `apisix` namespace to forward requests for `api-stage.crouseco.com` to the APISIX Service.

Manifest: `apisix-gateway-route.yaml`

```yaml
apiVersion: gateway.networking.k8s.io/v1
kind: HTTPRoute
metadata:
  name: apisix-gateway-route
  namespace: apisix
spec:
  parentRefs:
    - name: shared-gateway
      namespace: gateway-system
      sectionName: https
  hostnames:
    - api-stage.crouseco.com
  rules:
    - backendRefs:
        - name: apisix-gateway
          port: 80
```

### Configuration explanation

- `metadata.namespace: apisix`: the HTTPRoute is stored in the APISIX namespace.
- `parentRefs`: attaches the route to the existing Cilium Gateway.
- `sectionName: https`: associates the route with the Gateway's HTTPS listener.
- `hostnames`: matches requests for `api-stage.crouseco.com`.
- `backendRefs`: forwards matching requests to the `apisix-gateway` Service on port `80`.

The route uses the Gateway API's default path match, `PathPrefix: /`, so all paths for this hostname are forwarded to APISIX.

### Applying the HTTPRoute

The route was created with:

```bash
kubectl apply -f apisix-gateway-route.yaml
```

Kubernetes returned:

```text
httproute.gateway.networking.k8s.io/apisix-gateway-route created
```

## 6. HTTPRoute Verification

The route was checked using:

```bash
kubectl get httproute apisix-gateway-route -n apisix
kubectl describe httproute apisix-gateway-route -n apisix
```

The route status reported:

```text
Type:    Accepted
Status:  True
Reason:  Accepted
Message: Accepted HTTPRoute

Type:    ResolvedRefs
Status:  True
Reason:  ResolvedRefs
Message: Service reference is valid
```

This confirms that Cilium accepted the HTTPRoute and resolved the reference to the APISIX Service.

## 7. Connectivity Testing

The Gateway's HTTPS NodePort was tested directly from the Kubernetes control-plane host.

Command:

```bash
curl -k -i \
  --connect-to api-stage.crouseco.com:443:172.25.3.197:31792 \
  https://api-stage.crouseco.com/
```

Observed response:

```text
HTTP/1.1 404 Not Found
server: envoy

{"error_msg":"404 Route Not Found"}
```

The response came from Envoy, the proxy used by Cilium Gateway. It confirms that the connection reached the Cilium Gateway proxy, but it does **not** prove that the request reached APISIX.

The HTTPRoute status confirms that the route was accepted, but end-to-end forwarding to APISIX still needs to be verified.

An earlier request to the APISIX Service directly returned:

```text
HTTP/1.1 404 Not Found
```

That response confirmed that APISIX was reachable through its Service. At that time, no APISIX route had been configured to handle the requested `/` path.

## 8. APISIX Health Check

The APISIX pods were running and Kubernetes reported them as ready.

The readiness probe was:

```text
tcp-socket :9080
```

This means Kubernetes checks whether the APISIX proxy listener on port `9080` accepts TCP connections. It does not use the HTTP endpoint `/status/ready`.

The APISIX container image did not include `wget`, so an attempted `kubectl exec ... wget` inside the APISIX container failed because the executable was unavailable.

The status API on port `7085` has not been confirmed as configured or enabled in the current APISIX configuration.

## 10. Current Architecture Summary

At this point:

- APISIX is installed in the `apisix` namespace.
- APISIX is exposed internally through a `ClusterIP` Service.
- Cilium Gateway API provides the existing HTTPS entry point.
- The `apisix-gateway-route` HTTPRoute has been created and accepted by Cilium.
- The API hostname is `api-stage.crouseco.com`.
- End-to-end Cilium-to-APISIX forwarding has not yet been conclusively verified.
- Backend routing through APISIX has not yet been configured.
- The HTTPRoute is currently applied directly with `kubectl`; Git and Argo CD management are planned for later.
