# APISIX Ingress Controller Installation Runbook

**Purpose:** Repeat the APISIX Ingress Controller installation on another Kubernetes cluster using the same locally available Helm chart and internal image registry.

**Documented environment:** 2026-10-13. Adapt cluster-specific names, IPs, registry paths, credentials, and node labels before reuse.

## 2. Architecture and important distinction

- **APISIX** is the API gateway/data plane that handles requests and applies routes.
- **APISIX Ingress Controller** watches Kubernetes API resources such as Gateway API `Gateway` and `HTTPRoute`, then configures APISIX.
- **GatewayProxy** is an APISIX-specific custom resource that tells the controller how to connect to the APISIX Admin API/control plane.
- **GatewayClass** identifies the controller that manages a Gateway.
- **Gateway** is the APISIX-managed Gateway API object to which APISIX `HTTPRoute` objects can attach.
- The existing external entry point remains the Cilium Gateway `shared-gateway` in namespace `gateway-system`. Its `HTTPRoute` forwards external traffic to the `apisix-gateway` Kubernetes Service. Do not replace or modify that Cilium route as part of installing the APISIX controller.

The two Gateways have different jobs: Cilium receives external traffic and forwards it to APISIX; the APISIX-managed Gateway is the Gateway API configuration point for routes that APISIX should implement.

## 3. Prerequisites

1. Kubernetes cluster access with permission to install CRDs and create resources in `apisix`.
2. Helm installed and working.
3. APISIX already installed in namespace `apisix`, with the Admin API exposed internally by Service `apisix-admin` on port `9180`.
4. The local chart and controller subchart are present at `/root/apisix` and `/root/apisix/charts/apisix-ingress-controller`.
5. Internal registry access to the images listed above.
6. A Kubernetes Secret named `apisix-admin-credentials` in namespace `apisix`, containing the APISIX Admin API key under key `admin`. The Secret must contain the correct key for the target APISIX installation. Do not put the raw key in Git or this document.
7. If the controller must run only on frontend workers, those nodes must have the label `zone=frontend`.

Check the cluster and chart:

```bash
kubectl version
helm version
kubectl get nodes --show-labels
helm show chart /root/apisix
helm show chart /root/apisix/charts/apisix-ingress-controller
```

Check the namespace, Admin Service, and Secret metadata without printing secret values:

```bash
kubectl get namespace apisix
kubectl get service apisix-admin -n apisix
kubectl get secret apisix-admin-credentials -n apisix
kubectl get secret apisix-admin-credentials -n apisix -o go-template='{{range $k,$v := .data}}{{printf "%s\n" $k}}{{end}}'
```

The Secret should expose a key named `admin`. Never run a command that decodes or prints the key to a terminal/log.

## 4. Check the Gateway API CRDs before installing

Gateway API CRDs were already installed in this cluster (v1.5.1) and were being used by Cilium. **Do not install the controller chart's bundled standard Gateway API CRDs over the existing installation.** In particular, do not apply:

```text

```

Check the existing CRDs and classes:

```bash
kubectl get crd gateways.gateway.networking.k8s.io httproutes.gateway.networking.k8s.io gatewayclasses.gateway.networking.k8s.io
kubectl get gatewayclass
```

Expected in this cluster: Cilium's `cilium` and `cilium-nodeport` classes already exist. They should remain unchanged.

## 5. Install the APISIX-specific CRDs

Install the APISIX Ingress Controller custom resources from the chart:

```bash
kubectl apply -f /root/apisix/charts/apisix-ingress-controller/crds/apisixic-crds.yaml
```

Confirm that `GatewayProxy` is registered:

```bash
kubectl get crd gatewayproxies.apisix.apache.org
kubectl explain gatewayproxy.spec --api-version=apisix.apache.org/v1alpha1
```

This file installs APISIX-specific CRDs, including `GatewayProxy`. Do not confuse these with the standard Gateway API CRDs.

## 6. Configure the controller values overlay

The existing APISIX release values were kept in `/root/apisix-values.yaml`. A separate temporary overlay was used to enable and configure the controller:

`/tmp/apisix-ingress-controller-test-values.yaml`

```yaml
ingress-controller:
  enabled: true
  deployment:
    replicas: 1
    nodeSelector:
      zone: frontend
    image:
      repository: repository.crouseco.com/docker-proxy/apache/apisix-ingress-controller
      tag: "2.2.0"
      pullPolicy: IfNotPresent
    adcContainer:
      image:
        repository: repository.crouseco.com/docker-proxy/api7/adc
        tag: "0.27.1"
  config:
    disableGatewayAPI: false
  webhook:
    enabled: false
  gatewayProxy:
    createDefault: true
    provider:
      type: ControlPlane
      controlPlane:
        service:
          name: apisix-admin
          port: 9180
        auth:
          type: AdminKey
          adminKey:
            valueFrom:
              secretKeyRef:
                name: apisix-admin-credentials
                key: admin
  apisix:
    adminService:
      namespace: apisix
      name: apisix-admin
      port: 9180
```

Notes:

- `enabled: true` enables the controller subchart.
- `disableGatewayAPI: false` enables Gateway API support.
- The `manager` container runs the controller; `adc-server` is the ADC sidecar.
- `gatewayProxy.createDefault: true` asks the Helm chart to create the default `GatewayProxy` resource.
- The Admin key is loaded from a Kubernetes Secret using `secretKeyRef`; it is not embedded in the values file.
- `webhook.enabled: false` was the setting used for this installation. If you enable the webhook on another cluster, follow the chart's certificate and webhook requirements.
- The `zone=frontend` selector is environment-specific. Remove or adjust it if the target cluster uses different node labels.
- This was a temporary test overlay. For a repeatable production installation, store a reviewed overlay in a controlled configuration repository, but never store secret values in Git.

## 8. Upgrade the APISIX release to enable the controller

Back up the base values first:

```bash
cp /root/apisix-values.yaml /root/apisix-values.yaml.backup-$(date +%Y%m%d)
```

Run the Helm upgrade (this is the command used in the current cluster):

```bash
helm upgrade apisix /root/apisix \
  --namespace apisix \
  --values /root/apisix-values.yaml \
  --values /tmp/apisix-ingress-controller-test-values.yaml \
  --wait --timeout 10m
```

Helm applies the base values first and then the overlay; values in the overlay take precedence. This is an upgrade of the existing `apisix` release, not a separate Helm release for the controller.

Check the release and pods:

```bash
helm status apisix -n apisix
helm get values apisix -n apisix --all
kubectl get pods -n apisix -o wide
kubectl get deployment -n apisix
```

Expected controller pod: one replica, two containers (`manager` and `adc-server`), `2/2 Running`, scheduled to a frontend node when the selector is enabled. APISIX and etcd should remain healthy.

A Helm hook Job such as `apisix-etcd-pre-upgrade` may appear as `Completed`; that is not itself a failure. The job did not inherit the controller's node selector in the observed installation.

## 9. Check controller logs and Admin API connectivity

Find the controller pod and its container names:

```bash
kubectl get pods -n apisix -o wide
kubectl get pod -n apisix <controller-pod-name> -o jsonpath='{.spec.containers[*].name}{"\n"}'
```

Read logs using the actual container name (`manager`, not `apisix-ingress-controller`):

```bash

kubectl logs -n apisix deployment/apisix-ingress-controller -c adc-server --since=10m
```

Healthy evidence observed during installation included ADC successfully reading APISIX Admin API resources (HTTP 200 responses for routes/services and other resources). Startup socket messages or initial authorization errors should be assessed against current logs after startup; do not treat old transient startup lines as proof of a current failure. Stream-route requests returning errors can be expected if APISIX stream mode is not enabled and stream routing is not being used.

Check the Admin Service and endpoints:

```bash

kubectl get endpointslice -n apisix -l kubernetes.io/service-name=apisix-admin
```

## 10. Create the GatewayClass

The controller's `GatewayClass` was created at `/root/apisix-gatewayclass.yaml`:

```yaml
apiVersion: gateway.networking.k8s.io/v1
kind: GatewayClass
metadata:
  name: apisix
spec:
  controllerName: apisix.apache.org/apisix-ingress-controller
```

Apply and verify:

```bash
kubectl apply -f /root/apisix-gatewayclass.yaml
kubectl get gatewayclass apisix
kubectl describe gatewayclass apisix
```

Expected: `Accepted=True` and a message indicating that the class was accepted by `apisix-ingress-controller`. Keep the existing Cilium GatewayClasses; do not change their controller name.

## 11. Create the APISIX Gateway and reference GatewayProxy

The Gateway was created at `/root/apisix-gateway.yaml`:

```yaml
apiVersion: gateway.networking.k8s.io/v1
kind: Gateway
metadata:
  name: apisix-gateway
  namespace: apisix
spec:
  gatewayClassName: apisix
  infrastructure:
    parametersRef:
      group: apisix.apache.org
      kind: GatewayProxy
      name: apisix-config
  listeners:
    - name: http
      protocol: HTTP
      port: 80
      allowedRoutes:
        namespaces:
          from: All
```

Apply and check:

```bash
kubectl apply -f /root/apisix-gateway.yaml
kubectl describe gateway apisix-gateway -n apisix
kubectl get gateway apisix-gateway -n apisix -o yaml
```

**Important troubleshooting detail:** Initially, the Gateway showed `Accepted=False` with `gateway proxy not found`. The fix was to set `spec.infrastructure.parametersRef` to the existing `GatewayProxy` (`apisix-config`) in the same namespace. After applying that change, the Gateway showed `Accepted=True`, `Programmed=True`, and the listener showed `Accepted=True`, `Programmed=True`, `ResolvedRefs=True`. `Attached Routes: 0` is normal until an HTTPRoute is created.

The `GatewayProxy` is created by the chart when `gatewayProxy.createDefault: true`. Verify it:

```bash
kubectl get gatewayproxy apisix-config -n apisix -o yaml
```

Confirm the provider is `ControlPlane`, the service is `apisix-admin:9180`, and the Admin key reference points to Secret `apisix-admin-credentials`, key `admin`. Do not print the Secret's decoded value.

## 13. External entry point: keep Cilium in front of APISIX

The existing external route is in namespace `apisix` and points to the APISIX gateway Service:

```yaml
apiVersion: gateway.networking.k8s.io/v1
kind: HTTPRoute
metadata:
  name: apisix-gateway-route
  namespace: apisix
spec:
  parentRefs:
    - name: shared-gateway
      namespace: gateway-system
      sectionName: https
  hostnames:
    - api-stage.crouseco.com
  rules:
    - backendRefs:
        - name: apisix-gateway
          port: 80
```

This route is handled by **Cilium**, not APISIX. It exposes APISIX externally; APISIX still needs its own API route before a request will match. A `404 Route Not Found` from APISIX can simply mean no APISIX route exists yet.

Do not point an application HTTPRoute directly at the Cilium Gateway if the intention is for APISIX to apply API routing. For APISIX-managed routes, set `parentRefs` to `apisix-gateway`.

## 14. Cross-namespace backend references

If an `HTTPRoute` is in namespace `apisix` but its backend Service is in another namespace such as `stage`, Gateway API requires a `ReferenceGrant` in the backend Service's namespace to permit that reference. Example for the `crouseserviceloan` Service:

```yaml
apiVersion: gateway.networking.k8s.io/v1beta1
kind: ReferenceGrant
metadata:
  name: allow-apisix-to-loan-service
  namespace: stage
spec:
  from:
    - group: gateway.networking.k8s.io
      kind: HTTPRoute
      namespace: apisix
  to:
    - group: ""
      kind: Service
      name: crouseserviceloan
```

Check that the target cluster serves `ReferenceGrant` at `gateway.networking.k8s.io/v1beta1` before applying. This is needed for cross-namespace backend references, not for Services in the same namespace as the route.

## 15. Common errors and fixes

| Symptom | Check / fix |
|---|---|
| `gateway proxy not found` on Gateway | Add `spec.infrastructure.parametersRef` with group `apisix.apache.org`, kind `GatewayProxy`, and the actual GatewayProxy name, `apisix-config`. |
| Controller pod pending | Check `zone=frontend` exists on a node, image pull access, and pod events. |
| Image pull error | Verify the exact internal registry path/tag and registry trust/authentication. |
| `kubectl logs ... -c apisix-ingress-controller` fails | Use `-c manager` or `-c adc-server`. |
| Admin API 403 | Check the Secret key name/reference and ensure it matches the APISIX Admin API key; never expose the key in logs or documentation. |
| Gateway API resources not reconciled | Check `disableGatewayAPI: false`, `GatewayClass.spec.controllerName`, controller logs, and Gateway status conditions. |
| APISIX responds `404 Route Not Found` | Controller installation alone does not create an API route. Create and validate an APISIX-managed `HTTPRoute`. |
| Cross-namespace backend `ResolvedRefs=False` | Add a correctly scoped `ReferenceGrant` in the backend namespace. |
| Standard Gateway API CRD conflicts | Do not reapply `gwapi-crds.yaml` over the existing Gateway API installation. |

## 16. Version and portability notes

This runbook records the versions and paths observed in the current cluster. On a new cluster, first check the versions supported by the exact APISIX Ingress Controller release and chart, and inspect the chart templates/values before upgrading. The `/root/apisix` chart directory, the overlay in `/tmp`, the Secret, the existing Gateway API CRDs, node labels, and Services are all cluster-local prerequisites; they do not automatically exist on a second cluster.

For a reproducible GitOps setup, keep non-secret YAML and reviewed Helm values in Git. Create the Admin Secret through your approved secret-management process. Pin image tags and chart versions; avoid relying on mutable tags such as `latest` for dependencies.
