# APISIX etcd Local Storage Configuration

## 1. Purpose

APISIX uses etcd to store its configuration and state. In this Kubernetes cluster, etcd is deployed as a three-replica StatefulSet.

Because the cluster does not currently have a StorageClass or dynamic storage provisioner, we configured **static local PersistentVolumes (PVs)** on the frontend worker nodes.

Each etcd replica receives an 8 GiB PersistentVolumeClaim (PVC), backed by a local directory on its assigned worker node.

## 2. Storage Architecture

The storage is distributed across two frontend workers:

| etcd replica | Worker node | Local directory | PV name | Capacity |
|---|---|---|---|---|
| etcd-0 | `stage-workerf1` | `/var/lib/k8s-local-storage/apisix-etcd-0` | `apisix-etcd-pv-0` | 8 GiB |
| etcd-1 | `stage-workerf1` | `/var/lib/k8s-local-storage/apisix-etcd-1` | `apisix-etcd-pv-1` | 8 GiB |
| etcd-2 | `stage-workerf2` | `/var/lib/k8s-local-storage/apisix-etcd-2` | `apisix-etcd-pv-2` | 8 GiB |

**Total advertised capacity:** 24 GiB.

The directories reside on the workers' local filesystems. The three PVs advertise separate capacities but do not reserve separate physical disks or guarantee that 24 GiB of disk space is available.

## 3. Prerequisites

The worker nodes have local filesystem space available:

- `stage-workerf1`: approximately 56 GiB root filesystem, with 42 GiB available at the time of checking.
- `stage-workerf2`: approximately the same filesystem capacity and available space, as reported during setup.

Kubernetes initially had no PVs, StorageClasses, or storage provisioner. Consequently, the three etcd PVCs remained `Pending`.

## 4. Create the Local Directories

Run on `stage-workerf1`:

```bash
sudo mkdir -p /var/lib/k8s-local-storage/apisix-etcd-0
sudo mkdir -p /var/lib/k8s-local-storage/apisix-etcd-1
```

Run on `stage-workerf2`:

```bash
sudo mkdir -p /var/lib/k8s-local-storage/apisix-etcd-2
```

Verify the directories on each worker:

```bash
sudo ls -ld /var/lib/k8s-local-storage/apisix-etcd-*
```

The local directory must exist on the node specified by its corresponding PV. Kubernetes does not create the directory automatically.

## 5. Create the PersistentVolumes

The PV manifest is stored on `Stage-MasterF1` at:

```text
/root/apisix-local-pv.yaml
```

It defines three PVs, each with:

- Capacity: `8Gi`
- Access mode: `ReadWriteOnce`
- Volume mode: `Filesystem`
- Reclaim policy: `Retain`
- Storage class: empty (`""`)
- Volume type: `local`
- Required node affinity for the correct worker hostname

Apply the manifest:

```bash
kubectl apply -f /root/apisix-local-pv.yaml
```

The `local` volume configuration connects a PV to a path on a specific worker. The node affinity ensures Kubernetes schedules a pod using that volume onto the correct node.

The empty storage class allows these static PVs to match the existing PVCs, which were created without a StorageClass.

## 6. PersistentVolumeClaims

The APISIX Helm chart created the following PVCs in the `apisix` namespace:

```text
data-apisix-etcd-0
data-apisix-etcd-1
data-apisix-etcd-2
```

Each PVC requests `8Gi` with access mode `ReadWriteOnce`.

Kubernetes successfully bound the claims to the available local PVs:

```text
data-apisix-etcd-0 -> apisix-etcd-pv-0
data-apisix-etcd-1 -> apisix-etcd-pv-2
data-apisix-etcd-2 -> apisix-etcd-pv-1
```

The PVC-to-PV binding is not based on matching numeric suffixes; Kubernetes selected compatible available volumes.

## 7. Verification

Check the PersistentVolumes:

```bash
kubectl get pv
```

Check the PVCs:

```bash
kubectl get pvc -n apisix
```

Check the PV and PVC details:

```bash
kubectl describe pv apisix-etcd-pv-0
kubectl describe pvc data-apisix-etcd-0 -n apisix
```

Expected status for all three PVs and PVCs:

```text
Bound
```

Check the etcd and APISIX pods:

```bash
kubectl get pods -n apisix -o wide
```

A `Bound` PVC confirms that storage has been allocated to the claim. It does not, by itself, confirm that the etcd container can successfully write to the directory. Pod readiness and logs must also be checked after starting the Helm release.

## 8. Important Limitations

### Node dependency

Local PVs are tied to their worker nodes. If a worker becomes unavailable, a pod using its local volume cannot simply mount that same volume on another worker.

### No storage replication

The PVs do not replicate data between nodes. etcd provides its own replication across its members, but this does not remove the need for backups or appropriate failure-domain planning.

### Disk capacity

The `8Gi` capacity is advertised to Kubernetes. It does not impose a physical disk quota on the directory. Monitor filesystem usage to prevent the worker's disk from filling up.

### Reclaim policy

The PVs use `Retain`. If a PVC is deleted, the underlying data is retained for manual recovery or cleanup. Recreating a PVC does not automatically guarantee reuse of a retained volume.

### Permissions

The etcd container must have permission to write to its local directory. If etcd fails with a permission error, inspect the pod logs and the chart's security context before changing directory ownership.

```bash

kubectl get pods -n apisix -o wide

```

```bash

```

Run the disk commands directly on each worker.

## 10. Future Improvements

This configuration is suitable for the current cluster setup and initial APISIX deployment. For stronger production resilience, consider a supported replicated storage solution or dedicated storage infrastructure, regular etcd snapshots, and tested recovery procedures.
