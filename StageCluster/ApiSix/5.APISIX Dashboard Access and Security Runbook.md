# APISIX Dashboard Access and Security Runbook

**Purpose:** Configure secure access to the APISIX Dashboard in the Kubernetes cluster, including IP allowlisting, NGINX reverse proxy configuration, and Admin API protection.

**Environment:** Kubernetes, APISIX, APISIX Ingress Controller, Cilium Gateway API, Windows NGINX reverse proxy.

**Dashboard hostname:** `apisix-dashboard-stage.crouseco.com`

**Admin API:** `apisix-admin.apisix.svc:9180`

---

## 1. Understand the access path

The APISIX Dashboard is the administrative interface for managing APISIX. It uses the APISIX Admin API, which can modify gateway configuration and must be protected.

The Dashboard UI is served on the Admin API listener, typically on port `9180`, at `/ui/`.

For this environment, the recommended administrative access path is:

Administrator → Windows NGINX with IP restrictions → Secure administrative access to APISIX

Do not assume that the normal APISIX gateway Service on port `80` exposes the Dashboard correctly. The Admin API listener and the public API gateway serve different purposes.

## 2. Verify the installation

Run these commands on a control-plane node:

```bash
kubectl get pods -n apisix -o wide
kubectl get svc -n apisix
kubectl get gatewayclass
kubectl get gateway -n apisix
kubectl get httproute -A
```

Check the APISIX deployment configuration:

```bash
kubectl exec -n apisix deploy/apisix -- \
  sh -c 'grep -n -A 12 -B 3 "enable_admin_ui" /usr/local/apisix/conf/config.yaml'
```

Confirm that the embedded Dashboard UI is enabled. The exact configuration path depends on the APISIX version and configuration file.

## 3. Understand IP allowlisting

An IP allowlist defines which source IP addresses or networks may access an administrative endpoint.

For example:

| Configuration | Meaning |
|---|---|
| `192.168.11.50` | Allow one administrator IP |
| `192.168.11.0/24` | Allow addresses in that subnet |
| `10.20.0.0/16` | Allow addresses in that larger network |
| `deny all` | Deny all other source addresses |

**Replace all example addresses with the real, approved administrator or VPN addresses.** Do not copy the examples into production without verifying them.

### 3.1 Configure the NGINX allowlist

On the Windows NGINX server, add access restrictions to the Dashboard's dedicated HTTPS server block.

Example:

```nginx
server {
    listen 443 ssl;
    http2 on;
    server_name apisix-dashboard-stage.crouseco.com;

    ssl_certificate     D:/WebData/nginx-1.30.3/certs/public.crt;
    ssl_certificate_key D:/WebData/nginx-1.30.3/certs/private.key;

    # Replace with approved administrator or VPN addresses.
    allow 192.168.11.50;
    allow 10.20.0.0/16;
    deny all;

    location / {
        # Configure this upstream only if it securely reaches
        # the actual Dashboard/Admin UI listener.
        proxy_pass http://YOUR_RESTRICTED_ADMIN_UPSTREAM;

        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
    }
}
```

The upstream shown above is a placeholder, not a working endpoint. Configure it only after establishing a secure path to the actual Admin UI listener.

Important considerations:

- `allow` and `deny` control the source IP NGINX sees.
- If administrators connect through a VPN, allow the VPN's actual source address or approved subnet.
- If another reverse proxy sits in front of NGINX, the source IP may be the proxy's IP rather than the administrator's IP. Configure trusted-proxy handling carefully; never trust arbitrary client-supplied `X-Forwarded-For` headers.
- Keep the Dashboard on a dedicated hostname and do not apply these restrictions to the public API hostname unless that is intentional.

Validate and reload NGINX after editing:

```powershell
nginx.exe -t
nginx.exe -s reload
```

Run these commands from the directory containing your NGINX executable, or use its full path.

## 4. Configure APISIX Admin API IP Allowlisting

APISIX provides the `deployment.admin.allow_admin` configuration to control which source IP addresses can access the Admin API.

The Dashboard uses the Admin API, so these restrictions can also affect Dashboard access. The Admin API key is still required; an IP allowlist does not replace authentication.

### 4.1 Allow all IPv4 addresses

To allow requests from any IPv4 address at the IP-filtering layer, configure:

```yaml
deployment:
  admin:
    allow_admin:
      - 0.0.0.0/0
```

**Security warning:** This permits every IPv4 source address through the `allow_admin` IP filter. It does not disable API-key authentication, but it substantially increases exposure. Do not use this configuration for a publicly reachable Admin API in production.

### 4.2 Allow only specific IP addresses or networks

For production, prefer a list of trusted administrator and management addresses:

```yaml
deployment:
  admin:
    allow_admin:
      - 127.0.0.0/24
      - 192.168.11.50/32
      - 10.20.0.0/16
```

Replace these examples with the actual addresses required by your environment.

| CIDR | Meaning |
|---|---|
| `127.0.0.0/24` | Loopback range |
| `192.168.11.50/32` | One specific IPv4 address |
| `10.20.0.0/16` | A private IPv4 network |
| `0.0.0.0/0` | All IPv4 addresses |

The addresses APISIX sees may be different from the administrator's workstation address. Depending on the network path, they may be a proxy, node, or Pod address. Verify the actual source addresses before enforcing a restrictive policy.

### 4.3 IPv6 considerations

If IPv6 is enabled and supported in the deployment, `::/0` represents all IPv6 addresses. Do not add it unless allowing all IPv6 sources is explicitly intended.

### 4.4 Verify the current configuration

Inspect the installed Helm values:

```bash
helm get values apisix -n apisix -a
```

Inspect the APISIX configuration:

```bash
kubectl exec -n apisix deploy/apisix -- \
  sh -c 'grep -n -A 10 -B 3 "allow_admin" /usr/local/apisix/conf/config.yaml'
```

Confirm the configuration path and supported values against the installed chart version before changing anything.

### 4.5 Apply changes safely

1. Back up the current Helm values.
2. Update the source values file used to manage the APISIX release.
3. Confirm the chart supports the intended values structure.
4. Apply the change using the established Helm or GitOps workflow.
5. Verify that APISIX is healthy and the Dashboard remains accessible to approved administrators.
6. Verify that unapproved sources are denied.

Do not assume a configuration change has taken effect until the rendered configuration and actual access behavior have been checked.

### 4.6 Protect the Ingress Controller

The APISIX Ingress Controller also communicates with the Admin API to configure routes and other resources.

Before restricting `allow_admin`, identify the source addresses used by the controller and any other legitimate Admin API clients. A restrictive list that omits required clients can break reconciliation or Dashboard operations.

Keep the Admin API Service internal, protect the Admin API key in a Kubernetes Secret, and avoid exposing port `9180` through a public NodePort or unrestricted Gateway route.

**Recommended policy:** Use explicit trusted IP ranges for production. Allowing all IPv4 addresses should be reserved for controlled troubleshooting, if needed, and should be reverted afterward.

## 5. Choose a secure Dashboard access method

Recommended options, in order of simplicity and isolation:

### Option A — Kubernetes port-forward

Use an authenticated Kubernetes account with appropriate RBAC permissions.

```bash
kubectl port-forward -n apisix svc/apisix-admin 9180:9180
```

Then access the UI from a trusted administrative workstation using the local forwarded port:

`http://127.0.0.1:9180/ui/`

This method avoids publishing the Admin API through the public gateway. Use it only on a trusted workstation and do not expose the local forwarded port to other interfaces.

### Option B — Dedicated administrative reverse proxy

If browser access through `apisix-dashboard-stage.crouseco.com` is required:

1. Create a dedicated administrative access path to the Admin UI listener.
2. Apply a source-IP allowlist at the reverse proxy or VPN boundary.
3. Add authentication in addition to the IP allowlist.
4. Ensure the proxy exposes only the intended UI resources and does not unintentionally expose Admin API endpoints.
5. Restrict network access to the Admin API and verify that the public API hostname cannot be used to reach it.

Do not simply point the Dashboard hostname at the ordinary APISIX gateway Service and assume that `/ui/` will work.

## 6. Verify access restrictions

Perform the following checks from both an approved and an unapproved client network.

| Test | Expected result |
|---|---|
| Approved administrator opens the Dashboard | Allowed, subject to authentication |
| Unapproved IP opens the Dashboard | Denied by the access-control layer |
| Public client connects directly to Admin API port `9180` | Not reachable |
| Public API hostname is used for normal API requests | Continues working as intended |
| Controller accesses the Admin API | Continues working with its required credentials and network permissions |

For NGINX, inspect the access and error logs when testing denied requests. A `403 Forbidden` is expected for a request rejected by an NGINX `allow`/`deny` rule.

Check that the Admin API Service has no unintended external exposure:

```bash
kubectl get svc apisix-admin -n apisix -o wide
kubectl get ingress,httproute -A
```

Inspect any Gateway routes that could provide access to the Admin API. A ClusterIP Service is not externally exposed by itself, but other routes, proxies, or NodePorts can still create an access path.

## 7. Operational checklist

Before considering the Dashboard ready for use:

- [ ] Dashboard hostname uses HTTPS.
- [ ] Only approved administrator/VPN IPs can access the administrative endpoint.
- [ ] Authentication is required in addition to IP filtering.
- [ ] Admin API port `9180` is not publicly exposed.
- [ ] Admin API source restrictions are configured and verified.
- [ ] The APISIX Ingress Controller retains its required Admin API access.
- [ ] The Dashboard hostname does not interfere with the public API hostname.
- [ ] Access-denial and successful-login tests have been completed.
- [ ] Credentials are stored in Kubernetes Secrets or an approved secret manager.
- [ ] Configuration changes are recorded in the platform repository without secrets.

**Security principle:** An IP allowlist is one layer of protection, not a replacement for authentication, API-key protection, network isolation, and HTTPS.
