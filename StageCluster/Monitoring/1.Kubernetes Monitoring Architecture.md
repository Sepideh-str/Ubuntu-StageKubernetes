# Kubernetes Monitoring Architecture

## 1. Overview

The purpose of this architecture is to collect Kubernetes metrics locally and forward selected metrics to an existing external Prometheus server.

Kubernetes Prometheus acts as a local metrics collector, while the external Prometheus acts as the central monitoring and long-term storage system.

The communication between the two Prometheus instances uses **Prometheus Federation (Pull Model)**.

## 3. Components

| Component | Responsibility |
|---|---|
| Node Exporter | Collects Linux node metrics |
| Cilium | Collects CNI and network metrics |
| Cilium Operator | Collects operator metrics |
| Hubble | Provides network observability metrics |
| Kube-State-Metrics | Exposes Kubernetes resource metrics |
| Kubernetes Prometheus | Scrapes exporters and provides Federation |
| External Prometheus | Central metrics storage and monitoring |

## 4. Metrics Collection

Kubernetes Prometheus periodically scrapes the metrics endpoints exposed by the installed exporters and monitoring components.

The collected metrics are stored in its local Time Series Database (TSDB).

The following metrics sources are included:

- Node Exporter
- Cilium Agent
- Cilium Operator
- Hubble Metrics
- Kube-State-Metrics

## 5. Prometheus Federation

Federation allows an external Prometheus instance to retrieve selected metrics from another Prometheus instance.

The external Prometheus periodically requests metrics through the Kubernetes Prometheus `/federate` endpoint.

The external Prometheus controls which metric series it retrieves through PromQL label selectors.

Federation does not copy the complete historical database. It retrieves the available samples for selected time series at each scrape.

### Communication flow

1. Kubernetes Prometheus collects metrics from the exporters.
2. Metrics are stored in its local TSDB.
3. External Prometheus periodically scrapes the `/federate` endpoint.
4. Selected metric samples are stored in the external Prometheus TSDB.
5. The external Prometheus becomes the central location for monitoring and long-term retention.

## 6. Storage and Retention

Kubernetes Prometheus requires persistent storage to retain metrics across Pod restarts and rescheduling.

Initial proposed configuration:

| Setting | Value |
|---|---|
| Storage type | Persistent Volume |
| Storage request | 20 GiB |
| Local retention | 7 days |
| Retention size limit | 15 GB |
| Storage purpose | Local metrics collection |

These values are initial sizing estimates and should be adjusted according to actual ingestion volume.

The external Prometheus maintains its own independent storage and retention configuration.

### Storage considerations

- Kubernetes Prometheus must use persistent storage.
- Local retention is limited to avoid unnecessary disk consumption.
- External Prometheus is responsible for long-term metrics retention.
- The Kubernetes storage backend must be provisioned before deployment.

## 7. Network and Security

The Federation endpoint must be accessible from the external Prometheus server.

Security requirements:

- Use private network connectivity.
- Restrict access to the external Prometheus server.
- Enable TLS.
- Configure authentication.
- Do not expose the Federation endpoint publicly.
- Permit only the required network traffic.

The endpoint should be exposed through a restricted internal service or private network route, not the public application Gateway.

## 8. GitOps Deployment

All Kubernetes monitoring components should be managed through Argo CD.

The Prometheus Helm configuration should be maintained in the monitoring GitOps repository.

Proposed structure:

```text
monitoring/
├── prometheus/
│   ├── Chart.yaml
│   └── values.yaml
├── node-exporter/
├── kube-state-metrics/
└── applications/
```

The existing Cilium and Hubble installations remain managed independently.

## 9. Implementation Plan

1. Verify available Kubernetes storage options.
2. Provision persistent storage for Prometheus.
3. Add the Prometheus Helm chart to the internal Helm repository if required.
4. Create the Prometheus Helm values.
5. Configure exporter discovery and scrape targets.
6. Deploy Prometheus through Argo CD.
7. Verify metrics collection and local persistence.
8. Configure the secure Federation endpoint.
9. Configure the external Prometheus scrape job.
10. Verify that Kubernetes metrics are available in external Prometheus.

## 10. Expected Result

At the end of the implementation:

- Kubernetes Prometheus independently collects Kubernetes metrics.
- Kubernetes Prometheus maintains a limited local metrics history.
- External Prometheus retrieves selected metrics through Federation.
- External Prometheus stores the received metrics centrally.
- Monitoring configuration is maintained through GitOps.
- Kubernetes exporters do not need to be individually exposed to external infrastructure.
