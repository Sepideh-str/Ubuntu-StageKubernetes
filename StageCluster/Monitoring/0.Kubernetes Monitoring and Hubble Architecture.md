# Kubernetes Monitoring and Hubble Architecture

## 1. Overview

The Kubernetes monitoring architecture uses an internal Prometheus instance to collect metrics from Kubernetes nodes and monitoring components.

Cilium and Hubble provide additional network observability capabilities.

Although Hubble Metrics is integrated with Prometheus, Hubble Relay operates independently and is responsible for aggregating network-flow information from Hubble agents.

It is important to distinguish between metrics collection and network-flow communication.

## 2. Internal Prometheus Metrics Collection

The internal Prometheus instance is responsible for collecting and storing monitoring metrics from the following components:

| Component | Namespace | Metrics Port | Purpose |
|---|---|---:|---|
| Node Exporter | monitoring | 9100 | Operating-system and node metrics |
| Kube-state-metrics | monitoring | 8080 | Kubernetes resource and object-state metrics |
| Cilium Agent | kube-system | 9962 | Cilium networking and agent metrics |
| Cilium Operator | kube-system | 9963 | Cilium operator metrics |
| Hubble Metrics | kube-system | 9965 | Network observability metrics |

Prometheus uses Kubernetes service discovery to automatically discover the endpoints associated with these Services.

The discovered endpoints are filtered using relabeling rules and scraped at the configured interval.

The current recommended scrape interval is 30 seconds.

## 3. Hubble Architecture

Hubble is the network observability component of Cilium.

It provides visibility into network communication and traffic flows between Kubernetes workloads and nodes.

Hubble consists of several components with different responsibilities.

### 3.1 Hubble Agent

Hubble Agent runs as part of the Cilium Agent on Kubernetes nodes.

Its responsibilities include:

- Observing network flows.
- Collecting network communication information.
- Providing flow information to Hubble Relay.
- Exposing Hubble metrics for Prometheus.

Hubble Agent communicates with Hubble Relay through the Hubble server interface.

### 3.2 Hubble Relay

Hubble Relay aggregates network-flow information from Hubble agents across Kubernetes nodes.

Its responsibilities include:

- Connecting to Hubble agents.
- Aggregating network-flow information.
- Providing a centralized interface for accessing flow data.
- Supporting Hubble UI and Hubble CLI queries.

Hubble Relay is not the same as Hubble Metrics.

It is primarily responsible for network-flow aggregation rather than Prometheus time-series collection.

### 3.3 Hubble UI

Hubble UI provides a graphical interface for visualizing network communication within the Kubernetes cluster.

It obtains network-flow information through Hubble Relay.

It can be used to investigate:

- Communication between Kubernetes workloads.
- Network flows between namespaces.
- Allowed and denied traffic.
- Network connectivity problems.
- Application communication patterns.

## 4. Hubble Metrics vs. Hubble Relay

These components have different responsibilities.

| Feature | Hubble Metrics | Hubble Relay |
|---|---|---|
| Main purpose | Expose monitoring metrics | Aggregate network flows |
| Prometheus integration | Yes | Not currently configured |
| Communication | Prometheus scrapes metrics endpoint | Communicates with Hubble agents |
| Port | 9965 | 4244 for agent communication |
| Used by | Prometheus | Hubble UI and CLI |

Hubble Metrics exposes Prometheus-compatible metrics.

Hubble Relay provides access to network-flow information collected by Hubble agents.

Therefore, Hubble Metrics is included in the internal Prometheus scrape configuration, while Hubble Relay is not currently included as a scrape target.

## 5. Communication and Network Requirements

The monitoring and Hubble components require different network communication paths.

### 5.1 Prometheus Metrics Collection

The internal Prometheus instance connects to the monitoring endpoints.

| Source | Destination | Protocol | Port |
|---|---|---|---:|
| Internal Prometheus | Node Exporter endpoints | TCP | 9100 |
| Internal Prometheus | Kube-state-metrics | TCP | 8080 |
| Internal Prometheus | Cilium Agent | TCP | 9962 |
| Internal Prometheus | Cilium Operator | TCP | 9963 |
| Internal Prometheus | Hubble Metrics | TCP | 9965 |

These connections are used to collect and store monitoring metrics.

### 5.2 Hubble Relay Communication

Hubble Relay needs to communicate with Hubble agents running on Kubernetes nodes.

| Source | Destination | Protocol | Port |
|---|---|---|---:|
| Hubble Relay | Hubble Agent on Kubernetes nodes | TCP | 4244 |

This communication allows Hubble Relay to aggregate network-flow information from the cluster.

Port 4244 is independent of Prometheus scraping.

### 5.3 Hubble UI Communication

Hubble UI communicates with Hubble Relay to retrieve network-flow information.

This is a separate communication path from Prometheus metrics collection.

## 6. Architecture Overview

The following diagram illustrates the separation between metrics collection and network-flow observability.

```text
                 Kubernetes Cluster
                 ==================

                  Internal Prometheus
                          |
          +---------------+---------------+
          |               |               |
          v               v               v
     Node Exporter   Kube-state       Cilium Agent
       :9100         Metrics :8080      :9962
                                          |
                           +--------------+--------------+
                           |              |
                           v              v
                    Cilium Operator   Hubble Metrics
                       :9963             :9965


                 Hubble Flow Observability
                 =========================

                    Hubble Agents
                    (Cilium Nodes)
                          |
                          | TCP 4244
                          |
                          v
                     Hubble Relay
                          |
                          v
                       Hubble UI
```

The two paths serve different purposes:

1. Prometheus collects numerical metrics and stores them as time-series data.
2. Hubble Relay aggregates network-flow information and makes it available to Hubble UI and CLI.

## 7. Monitoring and Observability Responsibilities

| Component | Responsibility |
|---|---|
| Internal Prometheus | Metrics collection and time-series storage |
| Node Exporter | Node-level metrics |
| Kube-state-metrics | Kubernetes object-state metrics |
| Cilium Agent | Cilium networking metrics |
| Cilium Operator | Cilium operator metrics |
| Hubble Metrics | Network-related metrics |
| Hubble Relay | Network-flow aggregation |
| Hubble UI | Network-flow visualization |

## 8. Summary

The internal Prometheus instance collects metrics from all configured monitoring components, including Hubble Metrics.

Hubble Relay operates independently from the Prometheus scrape process. It communicates with Hubble agents on Kubernetes nodes to aggregate network-flow information.

Hubble UI uses Hubble Relay to visualize network communication.

Consequently, two separate communication requirements must be considered:

- **Metrics collection:** Prometheus to monitoring endpoints.
- **Network-flow observability:** Hubble Relay to Hubble agents over TCP 4244.

These communication paths should be documented and managed separately in Kubernetes network-access requirements.
