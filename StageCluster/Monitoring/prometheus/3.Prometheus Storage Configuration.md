# Prometheus Storage Configuration

## 1. Overview

Prometheus is deployed inside the Kubernetes cluster and uses persistent local storage to retain its time-series data.

For the initial deployment, a single Prometheus instance is used. Its storage is provided by a manually provisioned Kubernetes Local Persistent Volume (Local PV).

### Storage architecture

| Component | Configuration |
|---|---|
| Namespace | `monitoring` |
| Prometheus replicas | 1 |
| Storage type | Local Persistent Volume |
| Storage node | `stage-workerf1` |
| Local storage directory | `/var/lib/k8s-local-storage/prometheus` |
| PV name | `prometheus-pv` |
| PVC name | `prometheus-pvc` |
| PV capacity | 15Gi |
| Access mode | ReadWriteOnce |
| Reclaim policy | Retain |
| Prometheus retention | 7 days |
| Prometheus retention size | 12GB |

## 2. Storage Node Selection

Prometheus storage is located on `stage-workerf1`.

The node was selected because it has sufficient available disk space and memory for the initial Prometheus deployment.

Before configuring storage, the node's available resources were checked.

```bash
df -h /
free -h
```

The observed resources were:

- Root filesystem: 56GB total
- Used disk space: approximately 18GB
- Available disk space: approximately 37GB
- Total memory: approximately 7.2Gi
- Available memory: approximately 4.5Gi

The node uses an LVM-based root filesystem. The existing logical volume had no remaining free space in its volume group, so the existing LVM configuration was left unchanged.

## 3. Create the Local Storage Directory

A dedicated directory was created on `stage-workerf1` for Prometheus data.

```bash
mkdir -p /var/lib/k8s-local-storage/prometheus
```

Verify the directory:

```bash
ls -ld /var/lib/k8s-local-storage/prometheus
```

The directory is located on the node's local filesystem.

**Important:** Local Persistent Volumes depend on the availability of their assigned node. If `stage-workerf1` becomes unavailable, Prometheus cannot access this storage from another node automatically.

## 4. Create the PersistentVolume

A PersistentVolume (PV) represents the storage resource available to Kubernetes.

The Prometheus PV is manually provisioned and uses the `local` volume type.

File: `templates/prometheus-pv.yaml`

```yaml
apiVersion: v1
kind: PersistentVolume
metadata:
  name: prometheus-pv
spec:
  capacity:
    storage: 15Gi
  volumeMode: Filesystem
  accessModes:
    - ReadWriteOnce
  persistentVolumeReclaimPolicy: Retain
  storageClassName: ""
  local:
    path: /var/lib/k8s-local-storage/prometheus
  nodeAffinity:
    required:
      nodeSelectorTerms:
        - matchExpressions:
            - key: kubernetes.io/hostname
              operator: In
              values:
                - stage-workerf1
```

### PV configuration explanation

| Field | Purpose |
|---|---|
| `capacity.storage` | Advertises 15Gi of storage capacity to Kubernetes. |
| `volumeMode` | Uses a filesystem rather than a raw block device. |
| `accessModes` | Allows read/write access from a single node. |
| `persistentVolumeReclaimPolicy` | Retains the underlying data when the PVC is released. |
| `storageClassName` | Empty string indicates a statically provisioned volume without a StorageClass. |
| `local.path` | Specifies the directory on the Kubernetes node. |
| `nodeAffinity` | Restricts the volume to `stage-workerf1`. |

### Why use nodeAffinity?

A Local PV is physically tied to a particular Kubernetes node.

The node affinity ensures that Kubernetes only schedules workloads using this volume onto the node where the data exists.

In this configuration, the PV is restricted to:

```yaml
kubernetes.io/hostname: stage-workerf1
```

## 5. Create the PersistentVolumeClaim

A PersistentVolumeClaim (PVC) is a request for storage made by a workload.

The Prometheus PVC requests 15Gi and explicitly references the previously created PV.

File: `templates/prometheus-pvc.yaml`

```yaml
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: prometheus-pvc
  namespace: monitoring
spec:
  accessModes:
    - ReadWriteOnce
  storageClassName: ""
  volumeName: prometheus-pv
  resources:
    requests:
      storage: 15Gi
```

### PVC configuration explanation

| Field | Purpose |
|---|---|
| `namespace` | Creates the claim in the `monitoring` namespace. |
| `accessModes` | Requests ReadWriteOnce access. |
| `storageClassName` | Matches the static PV configuration. |
| `volumeName` | Explicitly binds the claim to `prometheus-pv`. |
| `resources.requests.storage` | Requests 15Gi of storage. |

The explicit `volumeName` ensures that this PVC is intended to bind to the Prometheus PV rather than another available volume.

## 6. PV and PVC Binding

The PV is a cluster-scoped Kubernetes resource, whereas the PVC belongs to a namespace.

The relationship is:

```text
PersistentVolume
    prometheus-pv
        |
        | Bound to
        |
PersistentVolumeClaim
    monitoring/prometheus-pvc
        |
        | Mounted by
        |
Prometheus Pod
    namespace: monitoring
```

Once both resources are created, Kubernetes should bind them.

Verify the PV:

```bash
kubectl get pv prometheus-pv
```

Verify the PVC:

```bash
kubectl get pvc -n monitoring prometheus-pvc
```

Expected status:

```text
STATUS: Bound
```

Inspect the complete configuration:

```bash
kubectl describe pv prometheus-pv
```

```bash
kubectl describe pvc prometheus-pvc -n monitoring
```

## 7. Integrate the PVC with the Prometheus Helm Chart

Prometheus is deployed using the `prometheus-community/prometheus` Helm chart through the internal Nexus Helm proxy.

The wrapper chart declares Prometheus as a dependency.

The Prometheus chart is configured to use the existing PVC instead of creating a separate dynamically provisioned claim.

Relevant configuration in `values.yaml`:

```yaml
prometheus:
  server:
    replicaCount: 1

    nodeSelector:
      kubernetes.io/hostname: stage-workerf1

    persistentVolume:
      enabled: true
      existingClaim: prometheus-pvc
      mountPath: /data
      storageClass: "-"

    retention: "7d"
    retentionSize: "12GB"
```

### Why use both nodeSelector and nodeAffinity?

Two separate scheduling constraints are configured:

1. PV `nodeAffinity` restricts the storage volume to `stage-workerf1`.
2. Prometheus `nodeSelector` explicitly schedules the Prometheus workload onto `stage-workerf1`.

This makes the workload placement intentional and consistent with the physical storage location.

The Prometheus configuration uses one replica, so this is a single-instance deployment rather than a highly available Prometheus setup.

## 8. Manage PV and PVC Through GitOps

The PV and PVC manifests are maintained inside the Prometheus wrapper chart:

```text
monitoring/
└── prometheus/
    ├── Chart.yaml
    ├── Chart.lock
    ├── values.yaml
    ├── charts/
    │   └── prometheus-29.45.0.tgz
    └── templates/
        ├── prometheus-pv.yaml
        └── prometheus-pvc.yaml
```

The PV and PVC are included in the Helm chart's `templates` directory.

This allows Argo CD to render and manage the storage resources together with the Prometheus deployment.

The workflow is:

1. Maintain the manifests and Helm values in GitLab.
2. Commit and push changes.
3. Argo CD detects the repository changes.
4. Argo CD renders the Helm chart.
5. Argo CD synchronizes the Kubernetes resources.

The PV is cluster-scoped and the PVC is created in the `monitoring` namespace.

## 9. Important Storage Considerations

### PV capacity is not a filesystem quota

The PV advertises a capacity of 15Gi to Kubernetes.

However, because this is a directory-backed Local PV, Kubernetes does not enforce a 15Gi filesystem quota on that directory.

The actual available space depends on the node's filesystem.

### Prometheus retention

Prometheus is configured with:

```yaml
retention: "7d"
retentionSize: "12GB"
```

These settings control how much historical time-series data Prometheus retains.

The 12GB retention-size setting is a Prometheus TSDB retention control, not a hard filesystem limit.

The node's filesystem should therefore be monitored to prevent disk exhaustion.

### Reclaim policy

The PV uses:

```yaml
persistentVolumeReclaimPolicy: Retain
```

This is intentional because Prometheus monitoring data should not be automatically deleted when its PVC is removed.

If the PVC is deleted, the PV can enter the `Released` state. The underlying directory and its contents remain on the node.

Manual cleanup and PV re-provisioning should be performed carefully.

### Availability

The current design has one Prometheus replica and local storage on `stage-workerf1`.

If this node becomes unavailable:

- The Prometheus pod cannot run on another node using the same local volume.
- Prometheus data remains on the unavailable node's disk.
- In-cluster metrics collection and federation become unavailable until the node and Prometheus recover.

The external Prometheus server retains metrics it has already scraped, but cannot federate new metrics while the in-cluster Prometheus is unavailable.

## Final Architecture

The resulting storage arrangement is:

```text
Kubernetes Cluster
|
+-- stage-workerf1
|   |
|   +-- /var/lib/k8s-local-storage/prometheus
|       |
|       +-- Local Persistent Volume
|           |
|           +-- prometheus-pv (15Gi)
|               |
|               +-- prometheus-pvc
|                   |
|                   +-- Prometheus Pod
|                       |
|                       +-- /data
|
+-- monitoring namespace
    |
    +-- Prometheus Deployment
        |
        +-- 1 replica
        +-- 7-day retention
        +-- 12GB retention-size limit
```

**Result:** Prometheus uses statically provisioned local storage on `stage-workerf1`, with its PV and PVC managed through the Prometheus Helm wrapper and Argo CD.
