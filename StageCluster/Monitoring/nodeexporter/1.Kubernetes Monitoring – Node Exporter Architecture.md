# Kubernetes Monitoring – Node Exporter Architecture

## 1. Overview

The Kubernetes cluster uses Node Exporter to expose Linux system metrics from its worker and control-plane nodes.

The external Prometheus server is responsible for collecting and storing monitoring metrics. An in-cluster Prometheus instance may be used temporarily for testing, troubleshooting and validating metric endpoints.

The objective is to maintain a centralized monitoring architecture without exposing unnecessary Kubernetes services externally.

## 2. Architecture

The monitoring architecture consists of the following components:

| Component | Location | Responsibility |
|---|---|---|
| External Prometheus | Outside Kubernetes | Primary metrics collection and storage |
| In-cluster Prometheus | Kubernetes | Temporary testing and troubleshooting |
| Node Exporter | Kubernetes | Exposes Linux node metrics |
| Kubernetes API | Kubernetes | Provides service discovery information |

### Metrics collection flow

External Prometheus discovers and scrapes Node Exporter endpoints individually.

```text
External Prometheus
        |
        | Metrics scraping (TCP 9100)
        |
        +---- Kubernetes Node 1
        |       Node Exporter
        |
        +---- Kubernetes Node 2
        |       Node Exporter
        |
        +---- Kubernetes Node 3
        |       Node Exporter
        |
        +---- Kubernetes Node N
                Node Exporter
```

## 3. Node Exporter Deployment

Node Exporter is deployed as a Kubernetes DaemonSet.

A DaemonSet ensures that one Node Exporter Pod runs on every eligible Kubernetes node.

This deployment model allows Prometheus to collect system metrics from each node independently.

### Collected metrics

Node Exporter exposes operating-system-level metrics, including:

- CPU utilization
- Memory utilization
- Filesystem capacity and usage
- Disk I/O
- Network interface statistics
- System load

## 4. Kubernetes Service Configuration

Node Exporter is exposed through a Kubernetes Service.

| Configuration | Recommended value |
|---|---|
| Service name | `node-exporter` |
| Namespace | `monitoring` |
| Service type | Headless (`clusterIP: None`) |
| Service port | `9100` |
| Target port | `9100` |
| NodePort | Not required |

A headless Service allows Kubernetes endpoint discovery to return individual Node Exporter endpoints rather than relying on a single load-balanced ClusterIP.

Prometheus can consequently scrape each Node Exporter instance independently.

## 5. Prometheus Service Discovery

Kubernetes endpoint discovery is used to identify Node Exporter instances.

The following configuration discovers endpoints belonging to the `node-exporter` Service and keeps only port `9100`.

```yaml
- job_name: 'node-exporter'
  kubernetes_sd_configs:
    - role: endpoints
      namespaces:
        names:
          - monitoring

  relabel_configs:
    - source_labels: [__meta_kubernetes_service_name]
      action: keep
      regex: node-exporter

    - source_labels: [__meta_kubernetes_endpoint_port]
      action: keep
      regex: "9100"
```

This configuration avoids discovering unrelated services and ports.

## 6. Network Requirements

External Prometheus must be able to reach the individual Node Exporter endpoints.

| Source | Destination | Protocol | Port | Purpose |
|---|---|---|---|---|
| External Prometheus | Kubernetes nodes | TCP | 9100 | Node Exporter metrics |

Network connectivity must be permitted between the external Prometheus server and every node hosting a Node Exporter instance.

NodePort is not required for this design when direct node IP connectivity is available.

If network segmentation prevents direct access, an appropriate internal exposure or collection architecture must be designed with the network team.

## 7. In-Cluster Prometheus

The in-cluster Prometheus instance is used during implementation and validation.

Its responsibilities include:

- Testing metrics endpoints.
- Validating Kubernetes service discovery.
- Checking target health.
- Identifying network connectivity problems.
- Verifying that metrics are successfully exposed.

It is not intended to become a second independent primary monitoring system.

After the external Prometheus integration is validated, the in-cluster instance can be removed if it is no longer required.

## 8. Validation

The following commands can be used to validate the deployment.

### Check the DaemonSet

```bash
kubectl get daemonset -n monitoring
```

### Check Node Exporter Pods

```bash
kubectl get pods -n monitoring -o wide
```

### Check the Service

```bash
kubectl get svc -n monitoring node-exporter
```

### Check discovered endpoints

```bash
kubectl get endpoints -n monitoring node-exporter -o wide
```

### Check Prometheus target health

```bash
curl -s 'http://localhost:9090/api/v1/targets?state=active'
```

The expected result is one healthy Node Exporter target per eligible Kubernetes node.

## 9. Design Decisions

The following decisions define the Node Exporter monitoring architecture:

1. Node Exporter runs as a DaemonSet.
2. A headless Service exposes individual Node Exporter endpoints.
3. Prometheus discovers endpoints through Kubernetes service discovery.
4. Each node is scraped independently on TCP port `9100`.
5. NodePort is not required.
6. External Prometheus is the primary monitoring server.
7. In-cluster Prometheus is used for temporary validation and troubleshooting.
