# Node Exporter Monitoring

## Overview

Node Exporter collects hardware and operating system metrics from Kubernetes nodes and exposes them through an HTTP endpoint on TCP port `9100`.

It runs as a Kubernetes DaemonSet, ensuring that one Node Exporter Pod runs on every eligible Linux node.

Prometheus discovers these Pods through Kubernetes service discovery and scrapes their metrics using their individual Pod IP addresses.

Each scraped target is associated with its Kubernetes node name, allowing metrics to be identified and grouped by node.

## Architecture

The monitoring architecture consists of:

1. **Node Exporter DaemonSet** – Runs one exporter Pod on each eligible node.
2. **Headless Service** – Exposes the individual Node Exporter Pod IP addresses through Kubernetes endpoints.
3. **Prometheus Kubernetes Service Discovery** – Discovers the Node Exporter endpoints through the Kubernetes API.
4. **Relabeling** – Attaches the Kubernetes node name to each discovered target.
5. **Cilium** – Provides Pod-to-Pod network connectivity between nodes.

### Monitoring flow

```text
                    Prometheus
                        |
                        |
             Kubernetes API Discovery
                        |
                        |
               Node Exporter Service
                 (Headless Service)
                        |
           +------------+------------+
           |            |            |
           v            v            v
       Exporter      Exporter     Exporter
         Pod           Pod          Pod

           v            v            v
       Kubernetes  Kubernetes   Kubernetes
         Node 1      Node 2       Node 3
```

Prometheus scrapes each exporter using its Pod IP. Kubernetes metadata identifies which node hosts each exporter Pod.

## 1. Node Exporter DaemonSet

Node Exporter is deployed as a DaemonSet in the `monitoring` namespace.

The DaemonSet uses host filesystem mounts to collect metrics from the underlying Kubernetes node.

Important configuration:

```yaml
spec:
  template:
    spec:
      hostNetwork: false
      containers:
        - name: node-exporter
          args:
            - --path.procfs=/host/proc
            - --path.sysfs=/host/sys
            - --path.rootfs=/host/root
            - --web.listen-address=0.0.0.0:9100
          ports:
            - name: metrics
              containerPort: 9100
              protocol: TCP
```

The exporter uses the following host filesystem mounts:

| Host path | Container path | Purpose |
|---|---|---|
| `/proc` | `/host/proc` | Process and CPU information |
| `/sys` | `/host/sys` | Kernel and hardware information |
| `/` | `/host/root` | Host filesystem information |

**Why `hostNetwork: false`?**

With `hostNetwork: false`, each Node Exporter Pod receives its own IP address from the Kubernetes Pod network.

This allows Prometheus to scrape the exporter through its Pod IP instead of connecting directly to the node IP on TCP port `9100`.

The host filesystem mounts still allow Node Exporter to collect metrics from the underlying node.

## 2. Node Exporter Headless Service

A Headless Service exposes the individual Node Exporter endpoints instead of providing a virtual ClusterIP.

```yaml
apiVersion: v1
kind: Service
metadata:
  name: node-exporter
  namespace: monitoring
  labels:
    app.kubernetes.io/name: node-exporter
spec:
  type: ClusterIP
  clusterIP: None
  selector:
    app.kubernetes.io/name: node-exporter
  ports:
    - name: metrics
      port: 9100
      targetPort: metrics
      protocol: TCP
```

The important configuration is:

```yaml
clusterIP: None
```

This creates a Headless Service.

Kubernetes maintains endpoint information for the matching Node Exporter Pods.

For example:

```text
Endpoints:
10.0.0.78:9100
10.0.1.52:9100
10.0.2.7:9100
...
```

Each endpoint represents an individual Node Exporter Pod IP and port.

To inspect the Service:

```bash
kubectl describe svc node-exporter -n monitoring
```

To inspect the associated endpoints:

```bash
kubectl get endpoints node-exporter -n monitoring -o wide
```

To identify the Pod IP and its Kubernetes node:

```bash
kubectl get pods -n monitoring -o wide
```

## 3. Prometheus Kubernetes Service Discovery

Prometheus uses native Kubernetes service discovery to discover Node Exporter endpoints.

The configuration is maintained under `extraScrapeConfigs`:

```yaml
- job_name: 'node-exporter'
  kubernetes_sd_configs:
    - role: endpoints
      namespaces:
        names:
          - monitoring

  relabel_configs:
    - source_labels: [__meta_kubernetes_service_name]
      action: keep
      regex: node-exporter

    - source_labels: [__meta_kubernetes_pod_node_name]
      target_label: node
```

### Kubernetes discovery role

The following configuration:

```yaml
role: endpoints
```

tells Prometheus to discover scrape targets using Kubernetes Endpoints resources.

Kubernetes provides the endpoint IP addresses and associated Pod metadata through its API.

The discovery process allows Prometheus to find the Node Exporter Pods without manually maintaining their IP addresses.

### Relabeling configuration

Prometheus uses relabeling to filter discovered targets and attach useful metadata.

**Filter by Service name**

```yaml
- source_labels: [__meta_kubernetes_service_name]
  action: keep
  regex: node-exporter
```

This keeps only endpoints belonging to the `node-exporter` Service.

**Attach the Kubernetes node name**

```yaml
- source_labels: [__meta_kubernetes_pod_node_name]
  target_label: node
```

Kubernetes discovery provides the metadata label `__meta_kubernetes_pod_node_name`.

The relabeling rule copies its value into a Prometheus label named `node`.

For example:

```text
node="stage-masterf1"
```

This allows Prometheus to identify which Kubernetes node each Node Exporter Pod represents.

## 4. Network Connectivity

Node Exporter listens on TCP port `9100` inside its Pod network namespace.

Prometheus connects to the exporter using its Pod IP:

```text
Prometheus Pod
      |
      | TCP 9100
      |
      v
Node Exporter Pod IP
```

Because the cluster uses Cilium with Geneve tunneling, cross-node Pod communication is transported through the Cilium overlay network.

The required Geneve traffic between nodes must be permitted by the underlying network firewall.

**Network requirements:**

- Prometheus Pod to Node Exporter Pod: TCP `9100`.
- Cilium Geneve tunnel between nodes: UDP `6081`.
- Kubernetes API access for Prometheus service discovery.

This design avoids requiring direct TCP `9100` connectivity between Kubernetes node IP addresses.

## 5. Verification

### Check Node Exporter Pods

```bash
kubectl get pods -n monitoring -o wide
```

Verify that:

- Node Exporter Pods are running.
- Each Pod has its own IP address.
- Each Pod is scheduled on the expected Kubernetes node.

### Check Service endpoints

```bash
kubectl describe svc node-exporter -n monitoring
```

Verify that the Service exposes the Node Exporter Pod IP addresses on port `9100`.

### Check Node Exporter metrics directly

```bash
curl http://<node-exporter-pod-ip>:9100/metrics
```

A successful response contains metrics such as:

```text
node_cpu_seconds_total
node_memory_MemAvailable_bytes
node_filesystem_avail_bytes
```

### Check Prometheus scraping

Prometheus exposes an HTTP API that can be queried without accessing its web interface.

For example:

```bash
curl -G http://<prometheus-service-ip>/api/v1/query \
  --data-urlencode 'query=up{job="node-exporter"}'
```

The `up` metric indicates whether Prometheus successfully scraped each target:

| Value | Meaning |
|---|---|
| `1` | Scrape successful |
| `0` | Scrape failed |

Example result:

```json
{
  "instance": "10.0.0.78:9100",
  "job": "node-exporter",
  "node": "stage-masterf1",
  "value": "1"
}
```

This confirms that Prometheus is scraping the exporter using its Pod IP and associating it with the correct Kubernetes node.

## 6. PromQL Queries

### Check all Node Exporter targets

```promql
up{job="node-exporter"}
```

### Count discovered targets per node

```promql
count by (node) (
  up{job="node-exporter"}
)
```

### CPU utilization per Kubernetes node

```promql
100 * (
  1 - avg by (node) (
    rate(node_cpu_seconds_total{
      job="node-exporter",
      mode="idle"
    }[5m])
  )
)
```

### Available memory per Kubernetes node

```promql
node_memory_MemAvailable_bytes{job="node-exporter"}
```

### Memory utilization percentage per node

```promql
100 * (
  1 -
  node_memory_MemAvailable_bytes{job="node-exporter"}
  /
  node_memory_MemTotal_bytes{job="node-exporter"}
)
```

## Summary

Node Exporter runs as a DaemonSet and collects metrics from the underlying Kubernetes nodes through host filesystem mounts.

A Headless Service exposes the individual exporter Pod IP addresses. Prometheus discovers these endpoints using Kubernetes service discovery with `role: endpoints`.

Relabeling attaches the Kubernetes node name to each target, allowing metrics to be queried and grouped by node.

Cilium provides the network connectivity required for Prometheus to scrape exporters across different Kubernetes nodes, without requiring direct TCP `9100` access between node IP addresses.
