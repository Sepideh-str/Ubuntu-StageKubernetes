# Kubernetes Monitoring – Node Exporter Architecture and Implementation

## 1. Overview

Node Exporter is deployed inside the Kubernetes cluster to expose Linux system metrics from individual Kubernetes nodes.

The external Prometheus server is responsible for collecting and storing monitoring metrics. An in-cluster Prometheus instance can be used temporarily for testing, troubleshooting and validating metric endpoints.

The monitoring architecture uses Kubernetes DaemonSet and endpoint discovery to collect metrics independently from each eligible node.

## 2. Architecture

| Component | Location | Responsibility |
|---|---|---|
| External Prometheus | Outside Kubernetes | Primary metrics collection and storage |
| In-cluster Prometheus | Kubernetes | Testing and troubleshooting |
| Node Exporter | Kubernetes | Exposes Linux node metrics |
| Kubernetes API | Kubernetes | Provides service discovery information |

### Metrics collection flow

```text
External Prometheus
        |
        | TCP 9100
        |
        +---- Node 1 (Node Exporter)
        |
        +---- Node 2 (Node Exporter)
        |
        +---- Node 3 (Node Exporter)
        |
        +---- Node N (Node Exporter)
```

Each Node Exporter instance is discovered and scraped independently.

## 3. Node Exporter Deployment

Node Exporter is deployed as a Kubernetes DaemonSet.

A DaemonSet ensures that one Node Exporter Pod runs on every eligible Kubernetes node.

This approach is appropriate for node-level monitoring because every node needs its own metrics exporter.

### 3.1 Deployment configuration

The DaemonSet manifest is maintained in `daemonset.yaml`.

```yaml
apiVersion: apps/v1
kind: DaemonSet
metadata:
  name: node-exporter
  namespace: monitoring
spec:
  selector:
    matchLabels:
      app.kubernetes.io/name: node-exporter
  template:
    metadata:
      labels:
        app.kubernetes.io/name: node-exporter
    spec:
      hostNetwork: true
      hostPID: false
      dnsPolicy: ClusterFirstWithHostNet

      nodeSelector:
        kubernetes.io/os: linux

      tolerations:
        - operator: Exists

      containers:
        - name: node-exporter
          image: repository.crouseco.com/docker-proxy/prom/node-exporter:v1.9.1
          args:
            - --path.procfs=/host/proc
            - --path.sysfs=/host/sys
            - --path.rootfs=/host/root
            - --web.listen-address=0.0.0.0:9100

          ports:
            - name: metrics
              containerPort: 9100
              protocol: TCP

          securityContext:
            allowPrivilegeEscalation: false
            readOnlyRootFilesystem: true
            capabilities:
              drop:
                - ALL

          resources:
            requests:
              cpu: 50m
              memory: 64Mi
            limits:
              memory: 128Mi

          volumeMounts:
            - name: proc
              mountPath: /host/proc
              readOnly: true
            - name: sys
              mountPath: /host/sys
              readOnly: true
            - name: root
              mountPath: /host/root
              readOnly: true

      volumes:
        - name: proc
          hostPath:
            path: /proc
            type: Directory
        - name: sys
          hostPath:
            path: /sys
            type: Directory
        - name: root
          hostPath:
            path: /
            type: Directory
```

### 3.2 DaemonSet configuration explanation

**Host networking**

```yaml
hostNetwork: true
```

This setting makes the Node Exporter Pod share the network namespace of its Kubernetes node.

Consequently, Node Exporter listens directly on the node's network interface at TCP port `9100`.

For example:

| Kubernetes node | Node Exporter endpoint |
|---|---|
| stage-masterf1 | `172.25.3.194:9100` |
| stage-masterf2 | `172.25.3.195:9100` |
| stage-masterf3 | `172.25.3.196:9100` |
| stage-workerf1 | `172.25.3.197:9100` |
| stage-workerf2 | `172.25.3.198:9100` |
| stage-workerd1 | `172.25.25.18:9100` |
| stage-workerd2 | `172.25.25.19:9100` |

Backend node addresses must be verified against the current Kubernetes node inventory.

This configuration allows Prometheus to collect metrics using individual node IP addresses without requiring NodePort.

**DNS policy**

```yaml
dnsPolicy: ClusterFirstWithHostNet
```

Because the Pod uses the host network, this DNS policy preserves Kubernetes cluster DNS resolution while using host networking.

**Node selector**

```yaml
nodeSelector:
  kubernetes.io/os: linux
```

This restricts Node Exporter scheduling to Linux nodes.

**Tolerations**

```yaml
tolerations:
  - operator: Exists
```

This allows Node Exporter to tolerate all taints, enabling scheduling on nodes that may have control-plane or other scheduling restrictions.

**Host filesystem access**

Node Exporter requires access to host operating-system information.

The following host paths are mounted into the container:

| Host path | Container path | Purpose |
|---|---|---|
| `/proc` | `/host/proc` | Process and kernel information |
| `/sys` | `/host/sys` | System and hardware information |
| `/` | `/host/root` | Host filesystem information |

All three mounts are read-only.

The corresponding command-line arguments tell Node Exporter where to find the host filesystem information instead of using the container's own filesystem.

**Security context**

The container uses a restricted security configuration:

- Privilege escalation is disabled.
- The container root filesystem is read-only.
- All Linux capabilities are dropped.

This reduces the container's privileges while allowing it to collect the required host metrics through read-only mounts.

**Resource allocation**

The container requests 50m CPU and 64Mi memory, with a memory limit of 128Mi.

These values define the initial resource allocation for the Node Exporter workload.

## 4. Kubernetes Service Configuration

The Node Exporter DaemonSet is exposed through a headless Kubernetes Service.

The Service manifest is maintained in `service.yaml`.

```yaml
apiVersion: v1
kind: Service
metadata:
  name: node-exporter
  namespace: monitoring
  labels:
    app.kubernetes.io/name: node-exporter
spec:
  type: ClusterIP
  clusterIP: None
  selector:
    app.kubernetes.io/name: node-exporter
  ports:
    - name: metrics
      port: 9100
      targetPort: metrics
      protocol: TCP
```

### 4.1 Service configuration explanation

**Headless Service**

```yaml
type: ClusterIP
clusterIP: None
```

A headless Service does not receive a virtual ClusterIP.

Instead, Kubernetes maintains individual endpoints for the Pods matching the Service selector.

Because Node Exporter uses `hostNetwork: true`, its Pod IP corresponds to its node IP.

Consequently, the Service endpoints identify the individual node addresses.

**Service selector**

```yaml
selector:
  app.kubernetes.io/name: node-exporter
```

This selector matches the labels assigned to the DaemonSet Pods.

It allows the Service to automatically discover the Node Exporter Pods.

**Service port**

```yaml
ports:
  - name: metrics
    port: 9100
    targetPort: metrics
```

The Service exposes TCP port `9100` and forwards it to the container port named `metrics`.

NodePort is not required.

### 4.2 Why use a headless Service?

A normal ClusterIP Service provides a virtual IP and can distribute connections between its endpoints.

For Node Exporter, the objective is to scrape every node independently.

A headless Service provides individual endpoint discovery instead of a single load-balanced destination.

This makes it suitable for Prometheus Kubernetes endpoint discovery.

## 5. Kustomize Configuration

The deployment resources are managed through Kustomize.

The directory contains the following files:

```text
node-exporter/
├── daemonset.yaml
├── service.yaml
└── kustomization.yaml
```

The `kustomization.yaml` file:

```yaml
apiVersion: kustomize.config.k8s.io/v1beta1
kind: Kustomization

resources:
  - daemonset.yaml
  - service.yaml
```

This configuration tells Kustomize which Kubernetes resources belong to the Node Exporter deployment.

Both manifests can be managed together through a single Kustomize application.

## 6. Applying the Configuration

The deployment can be installed or updated using:

```bash
kubectl apply -k .
```

Run the command from the directory containing `kustomization.yaml`.

## 7. Prometheus Service Discovery

Prometheus uses Kubernetes endpoint discovery to identify Node Exporter instances.

The following configuration discovers endpoints belonging to the `node-exporter` Service in the `monitoring` namespace.

```yaml
- job_name: 'node-exporter'
  kubernetes_sd_configs:
    - role: endpoints
      namespaces:
        names:
          - monitoring

  relabel_configs:
    - source_labels: [__meta_kubernetes_service_name]
      action: keep
      regex: node-exporter

    - source_labels: [__meta_kubernetes_endpoint_port]
      action: keep
      regex: "9100"
```

The relabeling rules:

1. Keep only endpoints belonging to the `node-exporter` Service.
2. Keep only endpoints exposing port `9100`.

Prometheus consequently discovers and scrapes the individual Node Exporter endpoints.

## 8. Network Requirements

Because Node Exporter uses host networking, its metrics endpoint listens directly on the Kubernetes node IP address.

External Prometheus must be able to establish TCP connections to every eligible node on port `9100`.

| Source | Destination | Protocol | Port | Purpose |
|---|---|---|---|---|
| External Prometheus | Kubernetes nodes | TCP | 9100 | Node Exporter metrics |

Network access must be permitted to all nodes hosting Node Exporter.

No NodePort exposure is required.

The headless Service is used for Kubernetes endpoint discovery; it does not provide external network connectivity by itself.

## 9. Validation

### 9.1 Check the DaemonSet

```bash
kubectl get daemonset -n monitoring
```

Verify that the number of ready Pods matches the number of eligible nodes.

### 9.2 Check Node Exporter Pods

```bash
kubectl get pods -n monitoring -o wide
```

Verify that there is one Node Exporter Pod on each eligible node.

### 9.3 Check the Service

```bash
kubectl get svc -n monitoring node-exporter
```

The Service should show:

```text
TYPE       CLUSTER-IP
ClusterIP  None
```

### 9.4 Check individual endpoints

```bash
kubectl get endpoints -n monitoring node-exporter -o wide
```

The endpoint list should contain the individual Node Exporter addresses and port `9100`.

### 9.5 Test a metrics endpoint

From a machine with network access to the node:

```bash
curl http://<NODE-IP>:9100/metrics
```

A successful response contains Prometheus-format metrics.

### 9.6 Check Prometheus targets

```bash
curl -s 'http://localhost:9090/api/v1/targets?state=active'
```

The expected result is one healthy target per eligible node.

The `up` metric can also be queried:

```bash
curl -s 'http://localhost:9090/api/v1/query?query=up{job="node-exporter"}'
```

A value of `1` indicates a successful scrape. A value of `0` indicates a failed scrape.

## 10. Design Decisions

The following decisions define the Node Exporter monitoring architecture:

1. Node Exporter runs as a DaemonSet.
2. Only Linux nodes are eligible for scheduling.
3. Host networking is enabled so the exporter listens directly on the node IP.
4. Host filesystem information is mounted read-only.
5. A headless ClusterIP Service provides individual endpoint discovery.
6. Prometheus discovers endpoints through Kubernetes service discovery.
7. Each node is scraped independently on TCP port `9100`.
8. NodePort is not required.
9. External Prometheus is the primary monitoring server.
10. In-cluster Prometheus is used for testing and troubleshooting.
