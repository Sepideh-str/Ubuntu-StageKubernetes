# Prometheus Scrape Configuration

## 1. Overview

Prometheus collects monitoring metrics from Kubernetes components and nodes using scrape jobs.

The `extraScrapeConfigs` configuration defines additional scrape jobs and uses Kubernetes service discovery to automatically identify monitoring targets.

This approach eliminates the need to manually configure IP addresses for individual monitoring components.

## 2. Scrape Jobs

The current configuration includes five scrape jobs:

| Job | Namespace | Kubernetes Service | Metrics Port |
|---|---|---|---:|
| node-exporter | monitoring | node-exporter | 9100 |
| kube-state-metrics | monitoring | kube-state-metrics | 8080 |
| cilium-agent | kube-system | cilium-agent | 9962 |
| cilium-operator | kube-system | cilium-operator | 9963 |
| hubble-metrics | kube-system | hubble-metrics | 9965 |

### 2.1 Node Exporter

Collects operating-system and node-level metrics, including:

- CPU utilization
- Memory usage
- Disk utilization
- Filesystem information
- Network traffic

### 2.2 Kube-state-metrics

Collects Kubernetes object-state metrics, including:

- Deployments and ReplicaSets
- Pods and their status
- Nodes and their conditions
- Namespaces
- Kubernetes resource information

### 2.3 Cilium Agent

Collects metrics related to Cilium networking and its agent operations.

### 2.4 Cilium Operator

Collects metrics related to Cilium operator operations and cluster networking management.

### 2.5 Hubble Metrics

Collects network observability metrics, including network flows and traffic information exposed by Hubble.

## 3. Kubernetes Service Discovery

Prometheus uses Kubernetes service discovery to automatically discover monitoring targets.

Example:

```yaml
kubernetes_sd_configs:
  - role: endpoints
    namespaces:
      names:
        - monitoring
```

Configuration explanation:

| Parameter | Description |
|---|---|
| `kubernetes_sd_configs` | Enables Kubernetes service discovery. |
| `role: endpoints` | Discovers endpoints associated with Kubernetes Services. |
| `namespaces` | Restricts discovery to specified namespaces. |
| `names` | Defines the namespaces to discover. |

For example, Prometheus discovers endpoints in the `monitoring` namespace without requiring manually configured IP addresses.

The Cilium jobs use the same mechanism but discover endpoints in the `kube-system` namespace.

## 4. Target Filtering with Relabeling

Kubernetes service discovery can discover multiple Services within a namespace.

The `relabel_configs` section filters the discovered targets so that each scrape job monitors only its intended Service.

Example:

```yaml
relabel_configs:
  - source_labels: [__meta_kubernetes_service_name]
    action: keep
    regex: node-exporter
```

Configuration explanation:

| Parameter | Description |
|---|---|
| `source_labels` | Specifies the Kubernetes metadata label used for filtering. |
| `action: keep` | Keeps targets matching the specified expression. |
| `regex` | Defines the Service name to match. |

For example, in the Node Exporter job:

- `node-exporter`: retained.
- `kube-state-metrics`: discarded.
- `prometheus-server`: discarded.

This ensures that each scrape job only monitors its intended targets.

## 5. Metrics Ports

Prometheus discovers endpoint addresses and ports through Kubernetes service discovery.

The configured Services expose the following metrics ports:

| Component | Port |
|---|---:|
| Node Exporter | 9100 |
| Kube-state-metrics | 8080 |
| Cilium Agent | 9962 |
| Cilium Operator | 9963 |
| Hubble Metrics | 9965 |

Unless explicitly overridden, Prometheus uses `/metrics` as the metrics endpoint path.

If a Service exposes multiple ports, additional relabeling may be required to ensure that only the intended metrics port is scraped.

## 6. Scrape Interval and Timeout

The scrape interval determines how frequently Prometheus collects metrics from each target.

The following configuration is recommended:

```yaml
prometheus:
  server:
    global:
      scrape_interval: 30s
      scrape_timeout: 10s
      evaluation_interval: 30s
```

| Parameter | Value | Description |
|---|---|---|
| `scrape_interval` | 30 seconds | Frequency of metrics collection. |
| `scrape_timeout` | 10 seconds | Maximum time allowed for an individual scrape. |
| `evaluation_interval` | 30 seconds | Frequency of alerting and recording rule evaluation. |

If no custom values are configured, Prometheus uses its default global scrape interval of 1 minute and evaluation interval of 1 minute.

The scrape timeout must not exceed the scrape interval.

## 7. Kubernetes RBAC Requirements

Prometheus uses the Kubernetes API to discover monitoring targets.

Its ServiceAccount requires appropriate permissions to discover Kubernetes resources.

For the current `role: endpoints` configuration, the required discovery permissions include:

- Services: `get`, `list`, `watch`
- Endpoints: `get`, `list`, `watch`

The Prometheus configuration and permissions should be maintained through Helm and GitOps.

## 8. Verification and Troubleshooting

### 8.1 Check Prometheus Targets

Prometheus provides a Targets page showing discovered monitoring endpoints and their scrape status.

```text
http://<prometheus-address>:9090/targets
```

To access Prometheus locally using port forwarding:

```bash
kubectl port-forward -n monitoring svc/prometheus-server 9090:80
```

Then open:

```text
http://localhost:9090/targets
```

A target with the status `UP` indicates that Prometheus successfully scraped its metrics endpoint.

A target with the status `DOWN` indicates a scrape failure.

### 8.2 Verify Scrape Status Using PromQL

Check Node Exporter:

```promql
up{job="node-exporter"}
```

Check Kube-state-metrics:

```promql
up{job="kube-state-metrics"}
```

Check Cilium Agent:

```promql
up{job="cilium-agent"}
```

Check Cilium Operator:

```promql
up{job="cilium-operator"}
```

Check Hubble Metrics:

```promql
up{job="hubble-metrics"}
```

Metric values:

| Value | Meaning |
|---|---|
| `1` | Target is successfully scraped. |
| `0` | Target scrape failed. |

### 8.3 Check Monitoring Services

```bash
kubectl get svc -n monitoring
kubectl get svc -n kube-system
```

Check discovered endpoints:

```bash
kubectl get endpointslice -n monitoring
kubectl get endpointslice -n kube-system
```

Check Prometheus logs:

```bash
kubectl logs -n monitoring deploy/prometheus-server
```

## 9. Storage and Retention

Prometheus uses a persistent volume to store collected time-series metrics.

The current configuration uses:

```yaml
persistentVolume:
  enabled: true
  existingClaim: prometheus-pvc
  mountPath: /data
  storageClass: "-"

retention: "7d"
retentionSize: "12GB"
```

The retention policies work together:

- `retention: 7d` limits stored data to seven days.
- `retentionSize: 12GB` limits the size of retained time-series blocks.

Whichever limit is reached first triggers deletion of older data.

The retention-size limit does not represent a strict limit on total PVC consumption because WAL files and other TSDB files also consume disk space.

Sufficient storage headroom should be maintained to accommodate these files.

## 10. Summary

The monitoring configuration uses Kubernetes service discovery to automatically identify and scrape metrics from five monitoring components.

The main advantages are:

- Automatic discovery of Kubernetes monitoring targets.
- No need to maintain individual node IP addresses manually.
- Separation of monitoring targets into dedicated scrape jobs.
- Centralized configuration through Helm values and GitOps.
- Configurable scrape intervals and data retention.
- Visibility into scrape health through Prometheus Targets and PromQL.
